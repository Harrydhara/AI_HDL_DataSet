# Lessons Learned

Throughout the DP1–DP4 design process, we learned that the most practical TinyQV design is not necessarily the design with the most features or the smallest area. The best final version was the one that balanced functionality, PPA, and security while still respecting the limits of a small hardware peripheral. Our original concept was a WiFi-assisted traffic-light controller, but the final design became more focused and defensible: the ESP32 acts only as a supplemental sensor, the legacy inductive-loop system keeps priority, and TinyQV decides when a WiFi-based request is valid.

One of the biggest lessons was that the ESP32 should not be treated as a fully trusted controller. In early versions, it was easy to think of the ESP32 as directly providing the information needed to control the traffic-light behavior. However, that would give too much authority to an external device. The final design limits the ESP32 to reporting WiFi count data through SPI. Control and threshold registers are protected from SPI writes and can only be changed through the RISC-V bus. This made the design smaller in authority, safer in behavior, and easier to justify from a security perspective.

We also learned that our generated design did not always match the system we originally brainstormed. Some early versions tried to put too much traffic-light timing logic on the chip instead of letting the existing legacy controller or 555-timer-style circuit handle the actual light timing. Other versions did not implement true SPI behavior and instead assumed the WiFi count was already available internally. Through iteration, we corrected the architecture so TinyQV receives the WiFi count through a true SPI slave input, stores the result internally, compares it against a threshold, and only asserts a supplemental request when the inductive loop is inactive.

Another major lesson was that SPI inputs should not be blindly trusted. Since SPI comes from an external ESP32, packets can be corrupted, replayed, spoofed, or generated by an unauthorized device with physical access. To address this, the final design added lightweight keyed CRC8 authentication, sequence-number replay checking, stale WiFi data timeout, and brute-force lockout after repeated invalid packets. These protections are not as strong as a full cryptographic authentication system, but they are much more realistic for the available area and timing constraints than implementing a large security block on TinyQV.

The PPA results also taught us an important tradeoff. DP2 showed that the design could be made much smaller, reducing the cell count from 145 cells to 59 cells and reducing area from 1448.889600 μm² to 751.9712 μm². However, that smaller version did not include the final security features. DP3 increased the design to 695 cells and 8155.3216 μm², but it added authentication, replay protection, timeout logic, lockout behavior, security status, and better input filtering while still achieving 177.84 MHz timing. From this, we learned that minimum area is not always the best final design goal, especially when the system interacts with safety-adjacent infrastructure.

We also learned that verification must include both valid and invalid behavior. It is not enough to test that a correct WiFi packet updates the count or that the request output turns on when congestion is detected. The testbench also needs to verify that bad packets are rejected, replayed packets do not update the design, stale WiFi data expires, lockout activates after repeated failures, and the inductive loop continues to override the supplemental WiFi request. These adversarial and edge-case tests made the final design more reliable than simply checking normal operation.

Finally, we learned that AI tools are most useful when they are used iteratively and critically. AI helped generate RTL, suggest optimizations, identify vulnerabilities, and create testbenches, but the team still had to decide which suggestions were practical. Some AI-generated ideas were too large, too complex, or not aligned with the intended legacy-controller architecture. The final design improved because we compared multiple AI suggestions, checked them against PPA/security requirements, and kept the parts that best matched the actual system goal.

Overall, the project taught us that a strong hardware design is not only about making the code work. It also requires defining trust boundaries, limiting external authority, protecting configuration registers, handling stale data, verifying failure cases, and choosing tradeoffs that match the real application. The final TinyQV peripheral is more secure, more realistic, and more defensible because it evolved from a general WiFi traffic-light idea into a constrained supplemental sensor interface with clear safety and security behavior.
