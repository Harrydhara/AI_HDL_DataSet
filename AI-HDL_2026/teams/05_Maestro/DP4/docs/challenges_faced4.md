# Challenge Faced
One of the biggest challenges we faced was deciding how to implement security in a way that was realistic for the TinyQV design. On one side, we considered stronger authentication methods that would provide better security, such as larger cryptographic tags or more advanced authentication logic. However, those options would require significantly more area, power, and design complexity. On the other side, relying only on the ESP32 to handle authentication would save chip resources, but it would leave the TinyQV peripheral blindly trusting an external device. Finding a practical middle ground was difficult. The final design uses a lightweight keyed CRC8 authentication tag, sequence-number checking, and lockout behavior, which gives the design more protection than an unauthenticated SPI interface while still fitting the constraints of a small hardware peripheral.

Another challenge was defining the correct trust boundary between the ESP32, the TinyQV peripheral, and the legacy traffic-light controller. Early versions of the design gave the ESP32 or the on-chip logic too much responsibility. Some versions attempted to handle more of the traffic-light timing directly on TinyQV, even though the intended system should let the existing legacy controller or 555-timer-style circuit handle the actual light timing. We had to refocus the design so TinyQV only acts as a supplemental demand detector. In the final version, the ESP32 reports WiFi count data, TinyQV authenticates and evaluates that data, and the legacy controller still keeps priority through the inductive-loop path.

We also struggled with staying focused on the specific task for each submission. As we gained a better understanding of the design, it became easy to get sidetracked by additional ideas, such as stronger encryption, more complex ESP32 behavior, full traffic-light timing, larger security logs, and more advanced firmware interaction. Many of these ideas were useful as future improvements, but they were not practical for the current submission. We had to separate what was necessary for the final design from what should be listed as future work.

A major technical challenge was balancing PPA against security. DP2 showed that the design could be made much smaller, reaching 59 cells and 751.9712 μm², but that version did not include the final security protections. DP3 added authentication, replay protection, stale-data timeout, lockout behavior, security status reporting, and loop filtering, which increased the design to 695 cells and 8155.3216 μm². This made the final design larger, but also more complete and defensible. The challenge was deciding that the larger design was acceptable because the added security features were directly related to the final submission goal.

Testing was another difficult part of the project. Once the design included true SPI behavior, authentication, sequence checking, timeout logic, lockout behavior, interrupts, and loop-detector priority, the testbench had to verify many more cases than the original design. It was not enough to show that a valid WiFi count could update the register. We also needed to show that invalid packets were rejected, replayed packets did not update the count, stale WiFi data expired, repeated authentication failures caused lockout, the security alert was triggered correctly, and the inductive-loop input still overrode the WiFi request. Creating test cases for both normal and adversarial behavior was more complicated than expected.

We also faced challenges interpreting the implementation results. Some optimizations improved area but hurt timing, while other security changes increased area but still allowed strong timing closure. This made it clear that PPA results cannot be judged from only one metric. For this design, area mattered, but timing, security behavior, and correct interaction with the legacy traffic-light system were also important. The final version was chosen because it provided the best overall balance rather than the smallest possible implementation.

Finally, working with AI-generated designs created its own challenges. AI tools helped us generate RTL, testbenches, and security ideas quickly, but the outputs were not always aligned with the exact architecture we wanted. Some generated versions assumed the WiFi count was already available instead of coming through true SPI. Other versions added too much control logic to the chip or did not clearly separate the ESP32 sensor role from the RISC-V control role. We had to review, compare, and revise the AI-generated suggestions so the final design matched the intended system.

Overall, the main challenges were choosing a realistic security approach, limiting the authority of the ESP32, avoiding unnecessary scope expansion, balancing PPA against security, and creating a testbench that could verify both normal and failure behavior. These challenges improved the final design because they forced us to define clearer trust boundaries, preserve the legacy controller’s priority, and justify each added feature in terms of functionality, timing, area, and security.
